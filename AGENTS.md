# AGENTS.md

This file provides project-specific guidance for Codex and other agentic coding tools in this repository.

Keep this file aligned with `CLAUDE.md`. Global/user-level operating rules live outside this repo; do not duplicate them here unless they are project-specific.

## Project Context

`brain-mcp-server` is the MCP server for Markdown-based AI Brain systems. It supports:

- local stdio operation against a filesystem Brain;
- hosted HTTP MCP operation on Fly.io;
- Supabase Postgres as the hosted revision, sync, source metadata, and operational telemetry store;
- Supabase Storage for source/artifact bytes.

Hosted Brain is the normal remote path for `ai-brain-jem`; local stdio remains the recovery and local-filesystem fallback.

## Current Operator Surfaces

- Hosted MCP endpoint: `https://jem-brain-mcp.fly.dev/mcp`.
- Local cockpit URL: `http://127.0.0.1:8787/`.
- Desktop launcher: generated by `npm run hosted:cockpit:launcher:install`.
- Cockpit LaunchAgent: generated by `npm run hosted:cockpit:launchd:plist`.

The cockpit is local-only and read-only. It must not expose Brain writes, conflict resolution, admin mutations, or public network binding.

## Telemetry Contract

Use Supabase Postgres for hosted operational telemetry.

- User-facing hosted MCP latency samples belong in `brain.sync_events` with `event_type = 'hosted_mcp_latency'`.
- Real hosted MCP server tool calls are the normal telemetry source and should use metadata `source = 'hosted_mcp_server'`.
- Telemetry must not record file content, patch text, source content, or search query text.
- The cockpit should read Postgres telemetry first.
- `.brain-sync/hosted-mcp-latency.json` is a fallback cache only, used when Postgres is unavailable or explicitly enabled.
- Do not introduce a new metrics database, daemon, or analytics service unless a backlog/spec promotion justifies it.

## Backlog And Specs

This project uses the layered backlog/spec system:

- `BACKLOG.md` is the one-line open-work inbox.
- `docs/specs/NNN-slug.md` is for promoted implementation briefs.
- `docs/DECISIONS.md` records durable decisions and rejected alternatives.

For user requests that capture open work, update `BACKLOG.md` narrowly. For shipped backlog work, remove the shipped line and leave durable detail in specs, docs, decisions, or commit history as appropriate.

## Verification

Use the smallest meaningful verification for the change, then broaden when shared behaviour is touched.

- Type-only or narrow config/doc checks: `npm run build` or focused `node --test ...`.
- Logic, schema, sync, hosted doctor, or cockpit changes: `npm run test`.
- Cockpit UI changes: verify the local browser surface on desktop and a narrow/mobile viewport when layout density changes.

## Supabase Safety

The `brain` schema is private. Do not grant `anon`, `authenticated`, or `public` access to Brain tables. Runtime access should use a dedicated database login that inherits `brain_runtime`.

After any migration touching schemas, RLS, functions, Storage, or user data access, rerun the security gate in `docs/security/hosted-brain-supabase-security-gate.md`.

Never commit, print, or paste Supabase service-role keys or database URLs.
