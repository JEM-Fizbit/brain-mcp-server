- Give doctor findings transient tolerance and an observation timestamp: today a single momentary failure is indistinguishable from a dead database. `checkPostgresSummary` wraps its query in a bare try/catch and turns **any** exception into `fail` (`scripts/hosted-doctor.mjs:521`), which maps to the `postgres_diagnostics_failed` action at `scripts/hosted-doctor.mjs:1476` with **urgency now** — no retry, no consecutive-failure threshold, no error classification. Observed 2026-08-20 on `ers-brain`: the cockpit showed `fail / postgres_diagnostics_failed / urgency now — getaddrinfo ENOTFOUND aws-1-eu-west-2.pooler.supabase.com` while nothing was actually wrong. Verified at investigation time — the hostname resolves (13.41.42.138 / 13.43.174.140), the pooler accepts TCP on both 5432 and 6543, the ERS doctor was overall `pass` with `postgres_summary` green (52 hosted files, 0 open conflicts, 90ms), and hosted `ers-brain` MCP calls had been succeeding throughout. `ENOTFOUND` is **name resolution**, not a refused connection, timeout or auth rejection: the local resolver is the router (192.168.0.1) and `pmset` shows the Mac cycling continuously through Sleep/DarkWake, so a poll landing in that window fails to resolve while the network stack is still returning. Four defects: (1) **no retry or threshold** — one blip is enough to latch the top severity; (2) **error classes are collapsed** — a DNS transient, a query timeout, a wrong password and a deleted database all render the identical banner and the identical "verify the profile database URL and Supabase reachability" remediation, so the message cannot direct the operator to the actual fault; (3) **findings carry no observation time** — the panel asserts "urgency now" for a condition that may have self-healed hours earlier, and its own remediation text ends with "reload Brain Monitor", which is a tell that the UI cannot distinguish *currently failing* from *failed once and never re-evaluated*; (4) **no history** — `hosted-doctor.out.json` is overwritten every cycle, so there is no way to tell a one-off from a recurring pattern, and the failing snapshot had already been overwritten before it could be examined. Fix direction: retry once or twice with short backoff before failing; classify the error and let only durable classes (auth, schema, permission, sustained unreachability) reach `fail` while transient network/DNS conditions degrade to `warn` with a recurrence count; stamp every finding with `observedAt` plus consecutive-failure count and surface both in the finding text; and retain a small bounded rolling history of doctor snapshots so recurrence is visible. **Promote together with the `db_max_span` item below** — same root cause (a transient or stale condition presented as a live incident), same cost (the checks most likely to catch a real regression are the ones the operator learns to dismiss), and most likely one shared fix in how findings are evaluated and rendered rather than two per-check patches.
