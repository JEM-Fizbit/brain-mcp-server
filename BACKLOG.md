- An approval timeout is indistinguishable from a denial or a tool failure, and an incapable call still burns an approval prompt before it fails. Repro 2026-08-01, claude.ai web: two `brain_ingest` calls returned only "No approval received" while John was away from the device and the prompt timed out; on the third call, with approval granted, the tool returned the real backend error (the postgres/filesystem refusal). Two distinct layers, and the triage question is which one owns each. **(a) Host layer** — the bare "No approval received" string is rendered by the MCP client/host, not this server, so the caller cannot tell whether to retry, and the reasonable inference at the time was that approval was *not* the blocker. Nothing here is fixable in this repo; route it as Anthropic product feedback alongside the existing OpenAI connector-UX feedback item below. **(b) Server layer** — the underlying precondition failure is only discoverable *after* a human approves, i.e. backend capability is checked after the approval gate rather than before. A capability probe that runs before the tool requests approval would let incapable calls fail fast with an accurate reason and no prompt at all. Adjacent to, but not covered by, the ordering-hazard clause of the hosted-ingestion item below: that clause is about failing before any *write* lands, this one is about failing before the *approval prompt* is raised. Captured via JEM Brain Capture/Triage 2026-08-01, transferred 2026-08-24.

- Give doctor findings transient tolerance and an observation timestamp: today a single momentary failure is indistinguishable from a dead database. `checkPostgresSummary` wraps its query in a bare try/catch and turns **any** exception into `fail` (`scripts/hosted-doctor.mjs:521`), which maps to the `postgres_diagnostics_failed` action at `scripts/hosted-doctor.mjs:1476` with **urgency now** — no retry, no consecutive-failure threshold, no error classification. Observed 2026-08-20 on `ers-brain`: the cockpit showed `fail / postgres_diagnostics_failed / urgency now — getaddrinfo ENOTFOUND aws-1-eu-west-2.pooler.supabase.com` while nothing was actually wrong. Verified at investigation time — the hostname resolves (13.41.42.138 / 13.43.174.140), the pooler accepts TCP on both 5432 and 6543, the ERS doctor was overall `pass` with `postgres_summary` green (52 hosted files, 0 open conflicts, 90ms), and hosted `ers-brain` MCP calls had been succeeding throughout. `ENOTFOUND` is **name resolution**, not a refused connection, timeout or auth rejection: the local resolver is the router (192.168.0.1) and `pmset` shows the Mac cycling continuously through Sleep/DarkWake, so a poll landing in that window fails to resolve while the network stack is still returning. Four defects: (1) **no retry or threshold** — one blip is enough to latch the top severity; (2) **error classes are collapsed** — a DNS transient, a query timeout, a wrong password and a deleted database all render the identical banner and the identical "verify the profile database URL and Supabase reachability" remediation, so the message cannot direct the operator to the actual fault; (3) **findings carry no observation time** — the panel asserts "urgency now" for a condition that may have self-healed hours earlier, and its own remediation text ends with "reload Brain Monitor", which is a tell that the UI cannot distinguish *currently failing* from *failed once and never re-evaluated*; (4) **no history** — `hosted-doctor.out.json` is overwritten every cycle, so there is no way to tell a one-off from a recurring pattern, and the failing snapshot had already been overwritten before it could be examined. Fix direction: retry once or twice with short backoff before failing; classify the error and let only durable classes (auth, schema, permission, sustained unreachability) reach `fail` while transient network/DNS conditions degrade to `warn` with a recurrence count; stamp every finding with `observedAt` plus consecutive-failure count and surface both in the finding text; and retain a small bounded rolling history of doctor snapshots so recurrence is visible. **Promote together with the `db_max_span` item below** — same root cause (a transient or stale condition presented as a live incident), same cost (the checks most likely to catch a real regression are the ones the operator learns to dismiss), and most likely one shared fix in how findings are evaluated and rendered rather than two per-check patches.
- Re-specify the `db_max_span` SLO: it is an un-windowed all-time max, so every cold start latches the doctor into `fail` for the length of telemetry retention. Observed 2026-07-29 on `ers-brain`: `user_operation_latency` = fail, "Max DB span breached fail threshold. 3555ms observed; warn at 500ms; fail at 2500ms" — while server read p95 was 546ms (warn 1000), write p95 254ms, and failed queries 0. The 3555ms span was a single `brain_search` (`scope: all`) at 16:03:27Z, seven minutes after the `ers-brain-mcp` machine started at 15:56:01Z (deployment v9); six more spans over 500ms clustered 16:03–16:40 plus one at 18:36, all `brain_search` bar one `brain_read_file`, and by 19:00–20:31 the median span was 7ms with a max of 302ms. Across the preceding eight days **no span exceeded 500ms** (all-time max 273ms), and the slow span returned `rowCount: 1`, so this was cold buffer/plan cache and fresh pooler connections after deploy, not row volume and not a regression. The metric as written therefore reports "urgency now" for a resolved warm-up blip and will keep doing so after every deploy, which trains the operator to ignore the one check most likely to catch a real regression. Fix, roughly in value order: (1) evaluate a rolling-window p99 or a last-24h max instead of an all-time max; (2) apply a warm-up grace period after a machine start — the deploy timestamp is already available to the doctor via the `fly_status` check; (3) at minimum surface breach age and sample position in the finding text ("3555ms, observed 7h ago, 1 of 554 spans") so a stale outlier cannot read as a live incident. Related but not covering it: the hosted-observability item below defers latency/SLO alerting "pending baseline distributions", and the operator-selectable time-window item covers the cockpit views (fixed 24H/7D), not this evaluator. Optional adjacent work: `brain_search` at `scope: all` is the heaviest path (FTS CTE over `brain_files+brain_file_revisions` plus the `source_artifact_text` join, and the owner of every slow event) — a post-deploy warm query would flatten the cold-start spike cheaply, mirroring the Workers cron warm-start pattern. **Shares a root cause with the doctor transient-tolerance item above** — a momentary condition rendered as a live top-severity finding — and the two should be promoted together as one piece of work on doctor finding semantics, not fixed check-by-check.
